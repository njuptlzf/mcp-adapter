# Phase 16 Plan 02 — Execute `git merge upstream/main` with v3.1 protocols

## Objective

Execute the first real `git merge upstream/main` using the v3.1 SKILL.md protocols.

**核心原则**：不预判任何文件的 §3.5 分类和处理策略。所有决策在 **merge 之后、分析代码和 commit 和 diff 时**才决定。

## ⚠️ 为什么不能预判

| 预判的风险 | 例子 |
|-----------|------|
| 预判"同文件不同段落 → 保留两侧" | 但如果两侧改的是**同一段落的同一行**，就不能保留两侧 |
| 预判"import 区域 → 保留 ours" | 但如果 theirs **删了**某个 import，就不能"两侧都保留" |
| 预判"同函数 → append mode" | 但如果两侧**改了同一行**，就是 replace mode，不是 append |
| 预判"§4.1 Default --theirs" | 但 §4.1 只在 §4.4 分析后决定"接受 upstream"时才适用 |

**正确流程**：merge → 跑 §3.5 分类 → 逐个 hunk 看 **ours 代码 + theirs 代码 + commit message + diff** → 按 §4.4 分析 → 决策。

## Tasks

### T1: Trigger merge (no auto-commit)

```bash
git checkout main
git merge upstream/main --no-commit --no-ff
# 记录实际冲突文件列表
git diff --name-only --diff-filter=U
```

### T2: Run §3.5 conflict hunk independence check

对每个 conflict 文件跑 §3.5 awk 脚本，**实际分类**每个 hunk：

```bash
git diff --name-only --diff-filter=U | while read f; do
  awk '
    /^<<<<<<< / { hunk=1; start=NR; next }
    /^=======/ { hunk=0; next }
    /^>>>>>>> / { hunk=0; end=NR; next }
    hunk && match($0, /^(export )?(async )?function ([A-Za-z_][A-Za-z0-9_]*)/, m) { fn=m[2] }
    /^>>>>>>> / { print FILENAME ": hunk@" start "-" end " in function: " fn }
  ' "$f"
done
```

**T2 输出**：每个 conflict hunk 的实际分类（同文件不同函数 / 同函数不同段 / 同函数同段 / import 区域）。

**注意**：awk 脚本只能识别"hunk 所在的函数名"——还需要 agent **阅读代码**确认分类是否准确（比如 import 区域冲突可能被误判为"顶层"）。

### T3: 对每个 conflict hunk 做 §4.4 分析

**对每个 hunk，agent MUST 执行以下分析（不跳过任何一个）**：

#### Step 1: Extract ours
```bash
git show :2:<file> | sed -n '<start>,<end>p'
```

#### Step 2: Extract theirs
```bash
git show :3:<file> | sed -n '<start>,<end>p'
```

#### Step 3: View function context
```bash
# 看 hunk 所在函数的完整上下文（ours 版本）
git show :2:<file> | sed -n '<fn_start>,<fn_end>p'
# 看 theirs 版本
git show :3:<file> | sed -n '<fn_start>,<fn_end>p'
```

#### Step 4: 分析 commit 和 diff
```bash
# 看 ours 的 commit 历史（这个文件最近 fork 改了什么）
git log upstream/main..main --oneline -- <file>

# 看 theirs 的 commit 历史（upstream 最近改了什么）
git log main..upstream/main --oneline -- <file>

# 看具体 diff（两侧各自改了哪些行）
git diff upstream/main...main -- <file>  # ours 的改动
git diff main...upstream/main -- <file>  # theirs 的改动
```

#### Step 5: 根据 Step 1-4 的分析结果决策

**按 §3.5 分类后的实际处理**：

**如果是"同文件不同函数"**：
- 检查 ours 和 theirs 是否真的改了不同函数 → 如果是 → **可以保留两侧**（拼接）
- 但如果两侧改的"不同函数"有**依赖关系**（如 ours 改了函数 A 的返回类型，theirs 改了调用 A 的函数 B）→ 不能简单拼接，需要分析兼容性

**如果是"同函数不同段"**：
- 检查两侧改的是否是函数内**不同行段** → 如果是 → 视内容：
  - append mode（一头一尾）→ 拼接
  - replace mode（同一中段）→ 需要阅读代码决策，可能选 ours、theirs 或手动合并
  - wrap mode（外包 + 内改）→ 嵌套合并

**如果是"同函数同段"**：
- 两侧改了**同一行** → 不能保留两侧，必须选一边或手动重写
- 走 §4.4 5 步完整分析 → 根据 commit message + diff + 代码语义决定

**如果是"import 区域"**：
- 检查两侧 import 的是否是**同一个 package 的不同版本** → 版本冲突 → 选兼容版本
- 检查一侧加了新 import，另一侧删了同一 import → 不能保留两侧，分析哪个是对的
- 检查两侧都加了不同 import → 可以都保留（追加）

**关键原则**：**不是所有冲突都可以保留两侧**。以下情况不能保留两侧：
1. 两侧改了**同一行**代码（同一行不能有两个值）
2. upstream **删除**了某段，fork **修改**了同一段（不能同时删除和保留）
3. 两侧改了**函数签名**（签名只能有一个）
4. 两侧 import 了**同一 package 的不兼容版本**

## 决策原则（不预判，仅描述规则）

### 什么时候可以"保留两侧"

✅ 可以保留两侧的条件（**全部满足**）：
1. §3.5 分类为"同文件不同函数"或"同函数不同段"
2. ours 和 theirs 改的是**互不影响的代码**
3. 合并后代码**语义正确**（不产生冲突的函数调用、类型不匹配等）
4. tsc 编译通过
5. npm test 通过

### 什么时候不能"保留两侧"

❌ 不能保留两侧的情况（**任一满足**）：
1. 两侧改了**同一行**代码
2. upstream 删除了某段，fork 修改了同一段
3. 两侧改了**函数签名**（签名只能有一个）
4. 两侧 import 了同一 package 的**不兼容版本**
5. 合并后代码**语义不正确**（如 ours 调用了函数 A，theirs 删除了函数 A）

### 什么时候走 §4.1 Default `--theirs`

§4.1 Default `--theirs` **仅在以下情况**适用：
1. §3.5 分类完成
2. §4.4 5 步分析完成
3. 分析结果决定"接受 upstream"（如 replace mode + theirs 更优）
4. **不是所有 `assess` 行都自动 `--theirs`**
